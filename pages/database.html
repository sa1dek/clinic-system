Overview / Database & Security
Persistence & protection

Keep clinic data organized and protected.

The README describes SQLite storage in a local database file, SQLAlchemy models and repositories, role-based access, and Argon2id password hashing.

▤

SQLite

The database is stored in clinic.db, a local file configured by DATABASE_URL.

⇄

SQLAlchemy ORM

Models define tables and relationships; repositories handle CRUD operations and queries.

⌑

Patient folders

The documented file structure keeps visit text and manually added imaging or lab files under a patient-specific folder.

Indexes described in the project

Patient lookup

ix_patient_full_name, unique ix_patient_code, and ix_patient_phone are listed for patient search fields.

Visit & expense queries

ix_visit_date, ix_visit_date_patient, and ix_expense_date_cat are listed for date-based and category-based queries.

Security controls documented

✓

Argon2id password hashing

The README says passwords are stored as hashes rather than plaintext and password strength is checked on change.

✓

Role-based access

Admin, doctor, and secretary roles have different documented permissions. Hiding a page alone is not a substitute for server-side or service-level authorization checks.

✓

Environment secrets

AI API keys are configured in .env, which should not be committed or shared publicly.

✓

Backups

The README recommends backing up both clinic.db and patients_files/. It also mentions backing up configuration separately and securely.

Important implementation caveat

These are controls described in the README, not a security audit. Real deployment should verify authorization checks, database backup restoration, file permissions, secret handling, encryption needs, and privacy obligations for medical data.
